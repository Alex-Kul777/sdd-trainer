# OpenSpec-основы (openspec-basics) — partial ## Goal После урока ты закроешь пробелы в понимании структуры change proposal и цикла работы OpenSpec. Сможешь описать анатомию change proposal: proposal.md (зачем) → design.md (как) → tasks.md (чек-лист) и объяснить, что происходит с дельтой спецификации после apply. Также ты научишься читать требования и сценарии спеки (SHALL/WHEN/THEN). ## Key concepts (с фокусом на твоих пробелах) - **OpenSpec** — не фреймворк для кода, а фреймворк для управления требованиями. Основа — структура `openspec/` в репозитории плюс CLI (`openspec`, v1.14.0), документация актуальна на 2025 год. - **Спецификация** — `openspec/specs/<capability>/spec.md`. Фиксирует «как есть» текущее инвариантное поведение: `## Purpose` + `### Requirement: ... SHALL ...` + `#### Scenario: WHEN ... THEN ...`. - *Почему*: с формулировкой **SHALL** мы задаём инвариант — правило, которое не должно меняться; **WHEN/THEN** даёт верную/неверную проверку, по спеке можно писать тесты и запускать `openspec validate`. - **Изменение (change proposal)** — `openspec/changes/<kebab-case>/` (например, `add-console-trainer/`). Это предложение изменений, а не истина. Анатомия change: - `proposal.md` — описание проблемы, решения и границ (scope). - `design.md` — технические решения; если не нужно — артефакт можно не создавать (достаточно задач). - `tasks.md` — чек-лист реализации. Без него нельзя начинать apply. - `specs/` — дельта требований (ADDED/MODIFIED) именно для этого change. - *Зачем дельта*: так мы фиксируем, что изменилось в поведении, и после apply переносим эти правки в `specs/`, в основную спеку. - **Жизненный цикл**: explore (читаем/проверяем спеку) → propose (создаём change с дельтой) → apply (реализуем по tasks, переносим дельту в `specs/`) → archive (сие change уходит в `changes/archive/`) - *Строгий формат* требования/кейса нужен для однозначности проверки и возможности авто-тестирования каждого шага: нельзя просто написать «требование», важно явно указать «SHALL», нельзя просто написать «кейс», нужно разбить на WHEN и THEN. ## Socratic questions (разбор твоих пробелов) - **Что содержится в каждом из файлов change proposal (proposal.md, design.md, tasks.md, specs/)?** - proposal.md — суть изменения и зачем оно нужно. - design.md — как планируется реализовать (опционально для сложных изменений). - tasks.md — список задач для выполнения. - specs/ — delta-спека, что именно поменялось в поведении (ADDED/MODIFIED). - **Почему именно чек-лист tasks.md обязателен для apply?** - apply начинает изменения только когда задачи определены, чтобы процесс был контролируемым. - **Если в change есть tasks.md, зачем ещё дельта спеки specs/?** - tasks.md — набор шагов, звёздочки минусуются; дельта-спека spec сохраняет знания о том, как изменились требования, и становится «истиной» в specs/ после apply. - **Что произойдёт с папкой change после apply?** - Она переместится в changes/archive/; её дельта-спека будет перенесена в specs/console-trainer/spec.md и помечена как ADDED/MODIFIED. ## Examples (разбавим сухость) 1. Читаю спеку из capability `console-trainer`: ``` ### Requirement: Routing With At Least Three Paths The routing node SHALL select между knows_it, partial, new_topic, плюс clarification #### Scenario: Route selected by assessment WHEN assess производит уровень уровня THEN route выбирает ровно один путь и это видно в логах сессии ``` Здесь _инвариант_: выбор всегда ровно одного пути (**SHALL**); проверка — _WHEN/THEN_. 2. Живой change proposal этого репозитория — `add-console-trainer`: - `proposal.md`: «скелет тренера без поведения, решение — вертикальный срез». - `design.md`: шиты на ADR-005/006/008/009, тестовый шов. - `tasks.md`: 7 групп задач с чекбоксами (знаем, что делать). - `specs/console-trainer/spec.md`: дельта с ADDED (добавлено новое требование). ## Quiz ref — мини-квиз для самопроверки Вопросы, на которые важно ответить: - Какие 3-4 файла лежат в change proposal? Зачем нужен каждый? - В чём разница между `specs/` и `changes/`? - Что делает `openspec apply`? Куда уходит архивная папка? - Почему формат требования должен содержать SHALL, а сценария — WHEN/THEN? - Привёл ли я практический пример применения change pipeline? ## Итог Ты уже понимаешь разницу между specs и changes; теперь закрепил структуру change proposal (proposal → design → tasks → delta-specs), цикл работы и практическую пользу инструментов (openspec apply, archive). Ученик
Методология, в которой спецификация, а не код — источник истины: план составляется до кода, спека остаётся контрактом, с которым сверяется каждая строка кода.
